## 1. RC Blocker 別の修正内容

### 1-1. P0 メモリ消費

原因（`p0-verify.md` §3、修正前 code の stage 計測で再現）:

| ID | 原因 | 計測での現れ方（list 10%、20,000 件） |
| --- | --- | --- |
| S1 | 要素ごとの tuple を入れ子にした sort key | render の peak 131.3 MiB に対し終了後 current 40.8 MiB |
| S2 | `report.dump` の chunk list | serialize の peak が出力 text の約 4.8 倍（195.7 MiB） |
| S3 | 全文の複製（`+ "\n"`、`.encode()`） | limit_check の peak = text + bytes（105.4 MiB） |
| S4 | 上限超過でも全文を作ってから判定 | 100% で上限の 2.6 / 3.1 倍の text を生成 |
| S5 | 収集 pass でも entry を保持・sort | 収集 pass の peak が本 pass と同じ |

修正（`iacreview/deltareport.py` のみ。import の制約 `__future__`・`json`・`re`・`dataclasses`・`typing`・`iacreview` は維持）:

1. 上限つき逐次直列化: `json.JSONEncoder(sort_keys=True, ensure_ascii=False, indent=2, separators=(",", ": "))` の `iterencode` を逐次消費し、chunk ごとに UTF-8 bytes を累積。上限を超えた chunk で中止（S2・S3・S4）。成功時の文字列は `report.dump` と同一
2. 出力 bytes の下限による事前判定: Change_Entry ごとに `193 + 13 × len(path)`、uncompared path ごとに `70 + 13 × len(path)` bytes。下限 > `MAX_OUTPUT_BYTES` なら render せず最小 Delta_Report と `output_size_limit_exceeded`（S4）
3. sort key の平坦化（順序は旧 key と同一。unit test で旧実装を oracle に比較）（S1）
4. 収集 pass は entry を保持・sort しない（S5）

代替案の比較（plan.md §2 D-1〜D-7）: 出力の逐次書き出しは途中結果を stdout に出すため不採用（上限超過時に部分結果を書かない要件）、`uncompared_paths` 件数の上限は失敗 Code の追加（Spec 変更）のため不採用、render の 1 pass 化は Design §10-2 の変更が要るため不採用。
