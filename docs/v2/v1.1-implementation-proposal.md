# v1.1 実装提案: Semantic Diff と Finding Delta

**本書は提案のみで、実装・file 作成は行っていない。** 記載の path はすべて「作成候補」である。
Baseline は commit `5e5ed36fe9cb26f58486806f04a9795d2332c83f`。根拠は `docs/v2/baseline-audit.md` と `docs/v2/reuse-and-gap-analysis.md` を参照。

## 1. 目的と位置付け

v1.1 は v2.0「Bounded Remediation」の Stage 4（Independent Verification）に必要な 2 つの決定論的部品を、Remediation より先に単独の機能として提供する。

1. **Template Semantic Diff**: 2 つの CloudFormation Template を Resource / Property 単位で比較する。
2. **Finding Delta**: 2 つの Review_Report を比較し、Finding を New / Resolved / Unchanged / Ambiguous に分類する。

どちらも Agent の判断を含まない決定論的処理とする（`.kiro/steering/development-principles.md`「決定論的処理と Agent 判断を分離する」）。Remediation（修正案生成・適用）は v1.1 に含めない。

## 2. 最小機能（v1.1 Scope）

### 2-2. 機能一覧

**MVP（v1.1 必須）**

1. Review_Report 2 つの読み込みと検証（`schema_version` MAJOR = 1、7-key envelope、各 Finding を `finding.from_dict` + `validate`）。
2. Finding Delta（4 分類、下記 2-3）。
3. Template Semantic Diff（file 入力）。
4. Delta Report の JSON 出力（決定論的、`report.dump` と同じ直列化規則）。
5. Delta Report の Markdown 出力（`--format markdown`）。
6. `iac-review-delta` Skill の `SKILL.md`。

**v1.1 内の任意機能（MVP の後に実装、別 PR）**

7. git mode: `--git-base REF --git-head REF --path PATH` で Template blob を read-only に取得して Semantic Diff に渡す。

### 2-3. Finding Delta の分類規則

前処理: 各 report の Finding を identity key で group 化する。`dedup` 済みのため、`Resource` 非 null かつ `Normalized_Category != "Other"` の Finding は同 Template 内で key が一意になる（`dedup.deduplicate` の性質）。

| 分類 | 条件 |
| --- | --- |
| **Unchanged** | 同じ key が base / head に 1 件ずつある。`Severity`, `FindingType`, `Confidence`, `Source` の差は `changes[]` に field 名で記録する（分類は変えない） |
| **New** | key が head のみにある |
| **Resolved** | key が base のみにあり、かつ head が「比較可能」: 該当 `Location.File` が head の `target.files` / `target.cdk.synthesized_templates` に含まれ、base Finding の全 `Source` が head の `sources_enabled` に含まれ、`tools[]` で available、その Source に起因する `errors[]` がない |
| **Ambiguous** | 次のいずれか。`reasons[]` に理由コードを記録する |

Ambiguous の理由コード（閉集合）:

- `not_dedup_eligible`: `Resource == null` または `Normalized_Category == "Other"`。ただし ID を除く canonical JSON が完全一致する組は Unchanged とする。
- `source_not_comparable`: Resolved 条件の Source / Tool / errors 要件を満たさない（Tool 不在で消えた Finding を Resolved と誤認しないため）。
- `template_not_reviewed`: 該当 file が片方の report の `target` に存在しない。
- `possible_logical_id_rename`: Semantic Diff が渡されたとき、同じ Type の Resource が 1 つ削除・1 つ追加され、その logical ID 間で同 category の Finding が移動している。
- `duplicate_key`: 同 key の Finding が片側に 2 件以上ある（dedup の不変条件が破れた入力）。

### 2-4. Semantic Diff の出力範囲

- `Resources`: logical ID 単位で `added` / `removed` / `modified`。`modified` は `type_changed`（bool）と、`Properties` および resource attribute（`DependsOn`, `Condition`, `DeletionPolicy`, `UpdateReplacePolicy`, `Metadata`）の変更 path 一覧（`{"path": [...], "change": "added|removed|modified"}`、path は `finding.canonical_template_path` で正規化）。
- `Parameters`, `Conditions`, `Mappings`, `Outputs`: 名前単位の added / removed / modified のみ。
- 比較対象は `yamlcfn` で long form に正規化された doc。list は位置で比較する（順序変更は modified として出る。既知の制約として明記する）。
- 値は出力しない（D-5）。

### 2-5. Delta envelope（案）

```json
{
  "delta_schema_version": "1.0.0",
  "base": {"schema_version": "1.0.0", "target": {}, "sources_enabled": [], "tools": []},
  "head": {"schema_version": "1.0.0", "target": {}, "sources_enabled": [], "tools": []},
  "entries": [
    {
      "classification": "New|Resolved|Unchanged|Ambiguous",
      "key": {"File": "...", "Resource": "...", "Normalized_Category": "..."},
      "base": null,
      "head": {"...": "13-field Finding をそのまま"},
      "changes": [],
      "reasons": []
    }
  ],
  "semantic_diff": null,
  "errors": [],
  "summary": {"new": 0, "resolved": 0, "unchanged": 0, "ambiguous": 0, "comparable": true}
}
```

- `base` / `head` に入る Finding は入力 report の 13-field dict をそのまま保持する（再採番しない）。
- `summary.comparable` は両 report の `errors[]` が空で、全 `tools[].available` が true のときだけ true。既存 `passed_all_checks` の意味は変えない。
- `entries` は `(classification 順, File, Resource or "", Normalized_Category, canonical JSON)` で sort し、決定論的にする。
- `errors[]` は既存 `StructuredError`（`errors.STRUCTURED_ERROR_KEYS`）を再利用する。

## 4. git mode の安全設計（任意機能 7）

| 脅威 | 対策 |
| --- | --- |
| ref injection（`--output=...`, `-c`, `--upload-pack=...`） | `-` で始まる ref を拒否。`assert_no_shell_metacharacters` を適用。`git rev-parse --verify --end-of-options <ref>^{commit}` で 40 桁 SHA に解決し、以後は SHA のみを argv に渡す |
| path traversal | `--path` は `report.normalize_output_path` で正規化（絶対 path・`..` 拒否）。repository root を `git -C <workspace> rev-parse --show-toplevel` で取得し、workspace 相対 path を repository 相対 path に変換する |
| symlink blob | `git ls-tree <sha> -- <path>` で mode を確認し、`100644` / `100755` の blob 以外（`120000` symlink、`160000` submodule、tree）は拒否する |
| 巨大 blob | `git cat-file -s <sha>:<path>` で事前に size を確認し、`template.MAX_TEMPLATE_BYTES`（5 MiB）超は `input_too_large` |
| untrusted repository config | worktree を読む command（`status`, `diff` の worktree 比較）は使わず、`rev-parse` / `ls-tree` / `cat-file` のみを使う。`cat-file blob` は `--filters` / `--textconv` を付けないため filter・textconv は適用されない。`-c core.fsmonitor=false` を付ける。これらの前提は regression test で確認する |
| 認証情報 | `proc.run` の env allowlist をそのまま使う（`AWS_*` を渡さない）。network を伴う command（`fetch` 等）は使わない |
| 書き込み | git に対する書き込み操作（checkout, worktree, stash 等）は一切行わない。一時 file を作らない（blob は memory 上で `template.parse_template_text` に渡す） |
| Tool 不在 / timeout | `toolcheck.require_tool` で `tool_unavailable` / `tool_version`、`proc.run` の timeout で `tool_timeout` |

未解決事項: `HOME` が渡るため user の global gitconfig は読み込まれる。`proc.run` の env allowlist を変えずに `GIT_CONFIG_GLOBAL` 等を設定する方法はないため、影響範囲を Known Limitation として記録する（`docs/v2/baseline-audit.md` S-2）。

## 6. テスト計画

テストの実行は既存 CI と同じ `python3 -m pytest --cov=iacreview --cov=benchmark/harness --cov-fail-under=80` で行う。

### 6-1. Unit

- `test_gitsrc.py`（任意）: `tmp_path` に作った一時 git repository で ref 解決と blob 取得。git 未導入環境では skip。

### 6-2. Integration

- `test_skill_iac_review_delta.py`: 既存 `run_iac_review.py` で作った base/head report を入力にした end-to-end。exit code、stdout が JSON / Markdown のみであること、stderr の診断。
- 既存 benchmark case（例: `benchmark/cases/case-002-public-s3`）の template を修正した fixture で、期待する Resolved が出ること。

### 6-3. Property（決定論性）

- `test_prop_delta.py`: 入力 report の `findings` 順序を並べ替えても出力が byte 一致する。同じ report 同士の比較は全件 Unchanged。base と head を入れ替えると New と Resolved が入れ替わる（Ambiguous を除く）。`PYTHONHASHSEED=random` の CI job に追加する。

### 6-4. Regression / Security

| テスト | 内容 |
| --- | --- |
| 不正 JSON report | 構文エラー、7-key でない envelope、`schema_version` MAJOR 不一致、Finding の schema 違反 → `schema_violation` で安全に失敗 |
| 不正 YAML / JSON template | `tests/fixtures/invalid/*`（`billion_laughs.yaml`, `python_object_tag.yaml` 等）を base/head に使い、既存と同じ `parse_failure` になる |
| Path traversal | `--base-report ../x`、外向き symlink、絶対 path → exit 7 |
| Shell metacharacter | 各引数に `;`, `|`, `$` 等 → exit 2 |
| Symlink | template / report の symlink、git の `120000` blob の拒否 |
| Git ref injection | `--git-base=--output=/tmp/x`, `-h`, `HEAD;id`, `HEAD^{tree}`, 存在しない ref → exit 2 または 3、git に option として渡らないこと |
| Tool 未導入 | `tests/fakebin/git-missing` で git mode が exit 5、file mode は影響を受けない |
| Timeout | `tests/fakebin/git-timeout` で `tool_timeout`、process group が回収される |
| 巨大入力 | 5 MiB 超の report / blob → `input_too_large` |
| Host path 漏えい | stdout に絶対 path が出ない（`tests/regression/test_sec_no_host_path_in_errors.py` と同じ観点） |
| Secret 非出力 | Template の値（NoEcho Parameter の Default 等）が Semantic Diff の出力に含まれない |

## 7. 互換性保証

v1.1 は以下を変更しない。

- 13-field Finding（`iacreview/finding.py` `Finding`, `FINDING_FIELDS`）と 4 つの追加制約（`validate`）。
- Review_Report の 7-key envelope（`report.REPORT_KEYS`）、6-key summary（`report.SUMMARY_KEYS`）、`schema_version = "1.0.0"`。
- `summary.passed_all_checks` の意味（`not findings`）。
- `errors[]` の 9-key StructuredError と `ERROR_CLASSES`（新しい error class は追加しない方針。必要になった場合は MINOR の追加として CHANGELOG に記録する）。
- 既存 5 Skill の CLI 引数、exit code、stdout。
- `cfn-guard-review` の `stats`。

Delta は独立した `delta_schema_version` を持ち、Review_Report の version とは別に管理する。

## 8. リスク

| リスク | 影響 | 対応 |
| --- | --- | --- |
| identity key が粗い（`(File, Resource, Category)`） | 同じ Resource・Category で原因が別の Finding が Unchanged と判定されうる（dedup と同じ粒度） | `changes[]` と Evidence の RuleId 差分を記録し、文書に「Delta は resource-category 単位」と明記する |
| logical ID の rename | Resolved + New に分かれる | `possible_logical_id_rename` で Ambiguous として人間に委ねる。自動追跡はしない |
| Source / Tool の版差 | cfn-lint の版が違うだけで New / Resolved が出る | 両 report の `tools[].version` を envelope に保持し、不一致を `summary` か `errors[]` で通知する |
| `passed_all_checks` の誤用 | Tool 不在を合格と誤認する | Delta 側で `comparable` を別途定義する |
| git config 経由の挙動変化 | untrusted repository で予期しない動作 | read-only command に限定し、regression test で確認する。残る Risk は Known Limitation として記録する |
| Baseline の 2 件 FAIL | v1.1 の PR が CI gate を通らない | 着手前に扱いを決める |
| list の位置比較 | 順序変更だけでも modified になる | 既知の制約として文書化する |
